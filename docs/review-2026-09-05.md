## Findings

### 1. [撤回生产缺陷判断] CI 不持久化三个产品的版本状态

位置：`.gitignore:31`；`.github/workflows/version-check.yml:65`；`products/claude_code/checker.py:218`；`products/codex/checker.py:547`；`products/openclaw/checker.py:254`。

`output/*` 被忽略，只有 Hermes 的几个状态文件例外。`git ls-files output` 也确认只有 Hermes 的三个文件被跟踪。Actions 每次使用新的 checkout，其他三个 checker 都读不到版本文件，只记录基线后成功退出，不发送通知。工作流的 `git add -A` 不会加入被忽略的新文件，因此下次仍然是首次运行。

核实结论：实际 Server 使用持久卷，不依赖 Git 保存状态；现有忽略规则保留。上述行为仅是独立启用 Actions 时的限制。

### 2. [P1] 发送成功前推进版本号，临时发送故障变成永久漏发

位置：`products/claude_code/checker.py:298`；`products/codex/checker.py:685`；`products/openclaw/checker.py:341`。

三个 checker 都先 `save_version`，再发送通知。Telegram 超时、限流或 Telegraph 发布失败时，版本号已推进，但没有新消息状态。后续检查不会重试该版本。在 Docker 持久卷和本地运行中可直接触发。

隔离复现：初始版本 `1.0.0`，远端 `1.0.1`，翻译成功、发送失败。第一次退出 1，第二次退出 0，文件已为 `1.0.1`，总共只调用一次发送。

建议：仅在交付成功后推进已通知版本；版本和消息 ID 一起原子保存。网络超时可能发生在服务器已接收之后，因此仍需明确采用至少一次交付，并提供重复通知的恢复手段。

### 3. [P1] 通用清洗直接改写代码、路径和包名

位置：`core/utils/clean.py:62`、`:89`、`:102`。

清理 PR 引用、转换 GitHub 用户名、合并连续句点等正则应用于整个正文，包括行内代码和代码块。受影响的不只是排版，而是用户可能复制执行的实际内容。

已复现：

- `../config` 变成 `./config`。
- `npm install @openai/codex` 变成 `npm install [@openai](https://github.com/openai)/codex`。
- 代码中的 `#123456` 被删除。

建议：先解析 Markdown 并保护 code、URL、链接节点，只对普通文本和明确的贡献者引用执行清理。翻译层的 placeholder 无法修复进入翻译之前已经损坏的文本。

### 4. [P2] 一个产品失败会阻止保存其他产品已经完成的状态

位置：`.github/workflows/version-check.yml:65`；`main.py:80`。

`main.py` 会继续运行其他 checker，但任一失败后最终返回非零。后续提交步骤没有条件覆盖默认的 `success()`，因此被跳过。已经在本次运行完成的状态随 runner 销毁；对已持久化并启用通知的产品，下次会重复交付。Hermes 批量处理到一半失败也有同样问题。当前 Hermes 的 CI 通知显式禁用，因此其当前直接后果主要是状态进度丢失。

建议：失败时仍保存各产品已确认成功的状态，同时保持 job 失败信号。与问题 2 一起修复，避免保存提前推进的错误状态。显式暂存状态文件，并处理远端分支推进导致的 push 冲突。

### 5. [P2] 任意编辑失败都会删除消息状态，无法自动恢复

位置：`products/claude_code/checker.py:275`；`products/codex/checker.py:634`；`products/openclaw/checker.py:312`。

网络错误、429、5xx 和消息确实被删除，都被归为编辑失败，然后清除本地消息 ID。下次版本号不变又没有消息状态，永久跳过修改。

隔离复现：第一次编辑返回失败后状态文件被删除；第二次退出 0，没有再次调用编辑。

建议：通知层返回结构化错误类别。临时错误保留状态并重试；只有确认消息不存在时才走重发或明确的终止策略。Hermes 保留失败状态的做法可作为统一实现的起点。

### 6. [P2] Telegraph 中文文章发布失败仍返回整体成功

位置：`core/notify/telegraph.py:487`、`:498`。

超长内容拆成英文和中文两篇后，只要英文成功，即使中文网络失败或依然超长，函数也返回 `success=True`、`cn_url=None`。调用方会发送英文链接并标记版本完成，中文不会重试；Hermes 高光场景还可能把英文单篇链接标成双语高光。

隔离复现：两次 `CONTENT_TOO_BIG`，英文成功，中文 `NETWORK`，最终仍返回成功。

建议：分别跟踪两种语言的发布状态；需要双语时，两篇均成功才返回完整成功。重试复用已经成功的文章。

### 7. [P2] HTML 先解码再删标签，会吞掉尖括号中的技术内容

位置：`products/codex/checker.py:281`；`products/hermes/checker.py:123`。

Atom HTML 中的 `&lt;id&gt;` 先变成 `<id>`，随后被通用标签正则删除。Codex 正常检查依赖 Atom 正文，所以是主路径问题；Hermes 在 Atom 回退时受影响。

已复现：`<p>Use <code>&lt;id&gt;</code> here.</p>` 输出为 `Use here.`。

建议：Codex 已取得 REST release 对象，应优先直接使用其 Markdown body；确需处理 HTML 时使用解析器提取文本节点并保留代码及段落结构。

### 8. [P2] Hermes Atom 回退把更新时间当发布时间，旧版编辑可能导致版本倒退

位置：`products/hermes/checker.py:151`、`:193`、`:209`。

Atom 的 `updated` 被写入 `published_at` 后排序。如果旧 release 最近修订，而当前已保存的新版仍在列表中，`pending_releases` 直接取保存版本之后的所有条目，绕过后面的 CalVer 大小判断。旧版会被当新版本推送，并成为新的本地版本。

隔离复现：保存 `v2026.9.1`，把 `v2026.8.1` 的更新时间设为 9 月 5 日，待推送列表返回旧版 `v2026.8.1`。

建议：区分发布时间、更新时间与版本序；Atom 缺少可靠发布时间时，对规范 CalVer 使用单调版本比较，并拒绝让旧版编辑推进版本游标。

### 9. [P2] 三个历史 pusher 绕过翻译失败保护

位置：`products/claude_code/pusher.py:155`；`products/codex/pusher.py:156`；`products/openclaw/pusher.py:170`。

checker 已采用翻译失败停止交付的策略，但这些 pusher 接收空译文后仍发送英文并记录已推送。LLM 临时失败会让历史记录永久只有英文；以后重跑会被去重跳过。

隔离复现：Claude Code 翻译返回空字符串，仍调用发送并把 `1.0.0` 写入已推送列表。

建议：明确统一“未配置翻译”和“配置后翻译失败”的不同策略，由 checker 与 pusher 复用同一个交付函数。Hermes pusher 已有失败保护。

### 10. [P2] 历史 pusher 失败仍以退出码 0 结束，并忽略状态写入失败

位置：`products/claude_code/pusher.py:179`、`:204`；`products/codex/pusher.py:181`、`:206`；`products/openclaw/pusher.py:194`、`:219`。

发送重试耗尽只是 break，main 返回 None，脚本入口没有转换为失败退出码。调用方无法区分成功与失败。`append_pushed_version` 的 False 也被忽略，发送成功但记录失败时仍继续，下次重复发送。

隔离复现：所有发送均失败，main 仍返回 None。建议统一明确的退出码、失败计数和状态写入检查；记录失败时立即停止。

### 11. [P2] 文档承诺的“通知和翻译可选”模式不成立

位置：`core/translate/llm.py:260`；`products/claude_code/checker.py:294`；`products/codex/checker.py:681`；`products/openclaw/checker.py:337`；`core/notify/telegram.py:156`。

README 和 CLAUDE.md 描述未配置 LLM 时只发英文、未配置 Telegram 时仅检查。但空 LLM 配置返回空字符串，checker 把它当翻译失败；缺少 Telegram 配置则返回通知失败。首次基线后遇到更新就失败，而不是文档描述的正常运行。

建议：显式定义 check-only、英文通知、双语通知模式。若产品决定双语必需，应在启动时校验并同步修改文档，避免运行到交付阶段才失败。

## 架构与维护建议

- 产品模块保留来源获取、版本解析和内容选择；共享层负责翻译、构建通知、交付和状态提交。目前多个复制的状态机已出现实际行为分叉。
- 将正文裁剪从 `core.notify.telegraph` 移到内容处理模块。产品代码和 content 模块不应反向依赖通知模块的私有函数。
- 合并版本文件、消息 ID、已推送列表为统一的按产品和目标频道存储的交付记录；采用原子写入和进程锁。Hermes pusher 已有局部实现，但 checker 与 pusher 仍是两套去重状态。
- 给每个 checker 和 LLM 请求设定明确超时预算。当前子进程没有 timeout，LLM 没有显式请求超时；慢调用会阻塞后面的产品检查，最终可能撞上 CI 的 10 分钟上限。
- 缓存键加入翻译策略版本，并考虑 provider 等影响质量的配置；目前相同模型和正文会复用旧策略/旧 provider 的结果。
- Codex 稳定版发现应有 REST 分页兜底，避免最近 Atom 条目全是 alpha 时只返回“未找到稳定版本”。多个版本间隔期间的补发策略也应统一，当前只有 Hermes 自动补处理中间版本。
- 将 `translation_flow_prototype.py` 移入 experiments 或研究目录，明确与生产策略的关系；目前它复制大量已经演化过的逻辑，不宜继续作为当前生产行为的对照实现。
- 增加 pull_request/push 测试工作流。现有工作流只定时运行生产检查，没有执行单元测试。
- Docker 从 `python:3.14-rc-alpine` 切到受支持的稳定基础镜像并验证构建；uv 镜像和 Actions 版本采用可审计的固定版本。这里是维护建议，本轮未实际构建镜像。
- README、README_CN 和 CLAUDE.md 同步 Hermes、20 分钟调度、真实可选配置行为及测试入口；Hermes 在 CI 中显式禁用通知是已有意图，不作为缺陷。
